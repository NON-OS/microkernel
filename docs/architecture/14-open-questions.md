# Open questions

Questions this review cannot settle from the code alone. Each states the options, what the review recommends where it has a view, and who has to decide. The decisions taken on them are recorded in [15-decisions.md](15-decisions.md); each question below names its entry there.

## Trust and attestation

1. **Should the attestation statement cover optional capabilities?** Today the trailer proves `(D_file, required_caps, epoch)` (`src/kernel_core/process_spawn/capsule_spawn/runner/preflight.rs:81`), so the Network bit a Linux network role adds (`src/userspace/capsule_linux/run_net.rs:35`) is bounded by the signed manifest and the certificate ceiling and is not proved. Proving the full approved set means one statement per role or per optional-bit combination, and re-proving every trailer. The verdict design keeps `proved_classes` separate so the gap is visible either way. *Decides*: the project maintainers, with the attestation pipeline's maintainers. *Decision*: [15-decisions.md](15-decisions.md), question 1.

2. **Should the statement move from `D_file` to `D_load`?** The target keeps today's statement over the file digest and has the pinned verifier vouch that `D_load` is the load digest of the same bytes ([09-target-spawn-and-boot-trust.md](09-target-spawn-and-boot-trust.md)). Proving over `D_load` directly removes the verifier from that link, at the cost of re-proving all 168 trailers (about 19 MB of proofs today) and changing the statement's definition in `nonos_attest_path`. *Recommendation*: keep `D_file` through the migration; revisit when the statement changes for another reason. *Decides*: the project maintainers. *Decision*: [15-decisions.md](15-decisions.md), question 2.

3. **Does the platform give the kernel its own TPM locality?** The target keeps one TPM command in ring 0, `PCR_Extend` of PCR 14 at locality 1, so the capsule log stays kernel-anchored while the rest of the driver runs in userland at locality 0 ([09-target-spawn-and-boot-trust.md](09-target-spawn-and-boot-trust.md), "PCR 14 and receipts"). That relies on the TPM's locality arbitration. On a platform whose firmware or TPM interface offers the OS only locality 0, the kernel and the tpm service would have to share one locality under a lock, which reintroduces a kernel dependency on a userland lock holder. *Decides*: a check of the shipped platforms' TPM interfaces (FIFO and CRB, discrete and firmware TPMs), then the owner. *Decision*: still open; [15-decisions.md](15-decisions.md) says what closes it.

4. **Where does the boot package live?** Inside the kernel image (the target's choice, which keeps today's property that the kernel signature covers every boot capsule) or as a separate file the bootloader verifies and measures, which would let a capsule update ship without re-signing the kernel. The second changes the bootloader's trust chain. *Decides*: the project maintainers. *Decision*: [15-decisions.md](15-decisions.md), question 4.

5. **How much does the measured-boot verdict gate?** Today a `Refused` verdict halts the boot in ring 0 (`src/kernel_core/init/entry/loader_refusal.rs:27-47`). In the target init gates the boot set on the attest service's verdict. Should a `SelfReported` verdict (no TPM, or no log) still boot, as today? The review keeps today's behaviour. *Decides*: the project maintainers. *Decision*: [15-decisions.md](15-decisions.md), question 5.

6. **Can one approved PCR 4 value per release cover the shipped platforms?** The rollback counter's increment policy binds increments to the enrolled loader through `PolicyPCR` on PCR 4 ([migration/tpm-rollback-floor.md](migration/tpm-rollback-floor.md)). PCR 4 depends on the firmware's boot path, so a release may need one approved value per platform family, or a different binding. Without some binding to the loader the signed approval is public and stops no increment; the harm left open is denial of boot, never rollback. *Decides*: a measurement of PCR 4 on the shipped platforms, then the owner. *Decision*: [15-decisions.md](15-decisions.md), question 6.

7. **Is the floor shadow's limit acceptable?** The shadow in the data volume's header heals a TPM reset and refuses older kernels after one, but an attacker who can both clear the TPM and write the disk can erase it. Closing that needs storage the attacker cannot write, which the PC platform does not offer the OS. *Decides*: the project maintainers. *Decision*: [15-decisions.md](15-decisions.md), question 7.

## The kernel's object model

8. **Kernel memory for objects: quota-charged heap, or untyped memory retyped by userland?** The target charges kernel allocations to a per-process quota and keeps the kernel heap ([07-target-object-model.md](07-target-object-model.md)). seL4's untyped-retype model removes the kernel heap from the proof and makes memory exhaustion attacks impossible by construction, at the cost of a larger change to `memory/` and to every service's bring-up. *Recommendation*: quota first; reconsider once the capability core is proved. *Decides*: the project maintainers, with whoever owns the proofs. *Decision*: [15-decisions.md](15-decisions.md), question 8.

9. **Flat capability table or guarded CNode tree?** A flat table of 4,096 slots per process is simpler to specify and is enough for every capsule in the catalogue; a tree scales and allows sharing a subtree between processes. *Recommendation*: flat. *Decides*: the kernel maintainers. *Decision*: [15-decisions.md](15-decisions.md), question 9.

10. **Are synchronous endpoints enough for every service?** Today's IPC is asynchronous named inboxes with bounded queues (`src/ipc/nonos_channel/message.rs:25`). Some services may depend on a sender not blocking (the supervisor's loop, the input ring, audio). The target offers notifications for events and shared MemoryObjects for streams; each service's protocol needs checking against that during phase 4. *Decides*: each service's maintainer, reviewed by the kernel maintainers. *Decision*: still open; [15-decisions.md](15-decisions.md) says what closes it.

11. **How long may old and new system calls coexist?** Through phases 3 and 4 the kernel carries both the 196 old calls and the 46 new ones, so ring 0 grows before it shrinks. *Decides*: the project maintainers, as a release-plan question. *Decision*: still open; [15-decisions.md](15-decisions.md) says what closes it.

12. **Port ranges through the TSS bitmap.** Granting PortRanges means a per-process I/O bitmap (up to 8 KiB) swapped on context switch for holders. Few drivers use port I/O (`ac97`, the VMware backdoor, legacy IDE). Keeping today's per-access system call for them is the alternative. *Recommendation*: the bitmap, since it removes the four port-I/O calls and a ring-0 `in` or `out` per access. *Decides*: the kernel maintainers, after measuring context-switch cost. *Decision*: [15-decisions.md](15-decisions.md), question 12.

## Components that stay trusted

13. **Does devmgr belong in the TCB for device-memory confidentiality between holders?** The kernel can require a completed `dev_reset` before a revoked Device is granted again ([10-target-device-authority.md](10-target-device-authority.md)); whether that reset clears the device's internal memory is device-specific and left to devmgr. *Decides*: the project maintainers. *Decision*: [15-decisions.md](15-decisions.md), question 13.

14. **One personality for many guests, or one per guest family?** The personality is trusted to separate the guests it serves, for their files and now for their network streams ([12-target-network-authority.md](12-target-network-authority.md)). An instance per family would make that separation the kernel's, at the cost of a personality spawn per family. The Linux startup measurements bear on this. *Decides*: the project maintainers. *Decision*: [15-decisions.md](15-decisions.md), question 14.

15. **Who restarts the verifier, devmgr and names?** Init does, from their pinned images. If init itself dies, the target resets the machine. Whether init should be split (a minimal root task that only restarts, and a second process that runs the spawn plan) depends on how large init's userland code turns out to be. *Decides*: the kernel maintainers after phase 2. *Decision*: [15-decisions.md](15-decisions.md), question 15.

## Scope

16. **Firmware tables before userland.** The kernel keeps a fixed-table reader for MADT, MCFG, DMAR, IVRS, HPET and FADT. The bootloader could instead hand over a digest of exactly these facts in the handoff, so the kernel parses no firmware table at all. That moves the parse into the bootloader, which is also trusted and already parses firmware data. *Decides*: the project maintainers. *Decision*: [15-decisions.md](15-decisions.md), question 16.

17. **Other architectures.** The aarch64 and riscv64 trees (47,100 phys lines, class X) were not classified in detail. The rule of [04-classification.md](04-classification.md) applies to them unchanged; whether to migrate them in step with x86_64 or after it is a release decision. *Decides*: the project maintainers. *Decision*: [15-decisions.md](15-decisions.md), question 17.

18. **Existing data volumes.** The volume's key derivation labels are bound to the caller's namespace inside the kernel today (`src/syscall/dispatch/crypto/machine_key.rs`, `src/fs/blockfs_volume/key_pick.rs:38`). The tpm service must reproduce exactly the same labels so existing volumes still open after phase 2. This is a compatibility constraint the tpm service's tests must pin. It is listed here because it fixes part of the badge format before the badge design is final. *Decides*: the volume and tpm maintainers. *Decision*: [15-decisions.md](15-decisions.md), question 18.
