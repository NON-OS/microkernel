# MediaTek MT7921 and MT7922

The mt7921e driver [capsule](../../overview/glossary-boot-root-record.md#capsule) runs the MediaTek MT7921 (MT7921E, AMD RZ608), MT7922 (AMD RZ616, in the ThinkPad T14 Gen 4 AMD among many) and MT7920 PCIe Wi-Fi cards: it brings the chip up, scans 2.4 and 5 GHz, joins WPA2 and WPA3 networks through the shared station and carries traffic for `net.core`.

## State

Host-proven only. No boot on a card has run it. Every statement below is read from the code and from `userland/mt7921_proofs`, which mounts the driver's own source over a modelled chip and MCU and a WPA2 access point: bring-up to `Ready`, a scan that hears the network, a WPA2 join that keys the link, and data sealed out and opened in. WPA3 (SAE) runs in the shared station's code, which this driver only carries frames for; no SAE access point is modelled here, so a WPA3 join through this driver is unproven on the host as well as on hardware. The [real-hardware checklist](../../hardware/real-hardware-checklist.md#mediatek-mt7921-and-mt7922) is its first test.

## Identity

The six ids of Linux v6.12's `mt7921_pci_device_table` (`drivers/net/wireless/mediatek/mt76/mt7921/pci.c`): 14c3:7961, 14c3:7922, 0b48:7922, 14c3:0608, 14c3:0616, 14c3:7920 (`userland/capsule_driver_mt7921/src/ids.rs`, `PCI_IDS`). The kernel's inventory (`src/hardware/inventory/mediatek_ids.rs`), the broker's scope row (`src/hardware/broker/scope_rows.rs`, `MT7921`) and Settings (`userland/capsule_settings/src/wifi/driver_ids.rs`) name the same six; `kernel_proofs` holds the inventory and the row to the driver's list and `scripts/check_driver_scope.py` the row. The chip is read back (`MT_HW_CHIPID`, `MT_HW_BOUND` bit 7 for the MT7920) and decides the firmware.

The kernel starts the capsule only when the boot scan found one of the six (`src/userspace/init/spawn_plan/drivers_wifi/mediatek.rs`). Its service is `driver.mt7921e0` on port 4266, reply port 4267 (`userland/capsule_driver_mt7921/Capsule.mk`).

## Authority

The mask 0xB8038: IPC, Memory, Crypto, Driver, DeviceEnum, Mmio and Dma, with Debug (0x100) optional, as the RTL8821CE's. No Irq: the rings are polled and the chip's interrupts stay masked. Crypto draws the station address (locally administered, never the card's own) and the handshake nonces. DeviceEnum also admits `MkInstallSource`, which is how the firmware package is read. No FileSystem, no Network.

Each stage prints one `[mt7921]` line and, when it fails, is the stage byte the Settings panel and the setup wizard read (`nonos_wifi_client::DriverStage`).

A firmware failure is retried three times (Linux retries ten), the card reset between attempts; after the third the WFDMA is stopped and Bus Master turned off, and the driver serves its stage.

### Where it departs from Linux

- Scanning is the shared station's: it tunes to a channel by a channel request (ROC) and listens, rather than sending `MCU_CE_CMD_START_HW_SCAN`; the station's own sweep, dwell and world-safe channel rules then apply unchanged, as on the other two drivers. A join holds its channel by a `JOIN` request, renewed before it lapses, until the BSS context takes the channel at association.
- Keys are never installed in the chip: CCMP runs in software in the shared station, so every frame crosses the ring in the clear and the chip is told nothing about keys.
- Every frame goes out at a fixed rate: management at the band's lowest, data at the fastest basic rate the AP named.
- No CLC or SAR power tables are sent: the firmware's defaults apply.
- No interrupts, no power save, no 6 GHz, no header translation, no A-MSDU de-aggregation.

## The firmware package

The firmware is not in the tree, in the capsule or in the kernel. Linux-firmware's six files at commit bf992df7a95b5e19bb8f8546eb4d7c53ab2598d0 (the MT7961, MT7961_1a and MT7922 patch and RAM code; WHENCE: Redistributable, `LICENCE.mediatek`) are pinned once, by name, length and sha256, in `userland/capsule_driver_mt7921/src/fw/pins.rs`.

- The image build places them, with `LICENCE.mediatek`, at `EFI/nonos/firmware/mediatek/` on the boot medium: `scripts/firmware_package.py`, called by `make nonos-mk-esp` from a linux-firmware tree (`NONOS_FIRMWARE_SOURCE`) or fetched once into `target/`; the nix artifact tree carries them under `firmware/mediatek/` (`tools/nix/firmware.nix`). A medium packed without them still boots; the driver then reports stage 10.
- The loader reads each file into loader memory and records it as a handoff module, kinds 0x20 to 0x25 (`nonos-bootloader/src/entry/firmware_package.rs`). It checks nothing about them.
- The kernel serves those kinds through `MkInstallSource` to a holder of DeviceEnum (`src/syscall/microkernel/install_source_kinds.rs`, `is_firmware`).
- The driver reads its chip's two files and refuses either unless its length and sha256 are the pinned ones (stage 11).
- `scripts/check_mediatek_firmware.py`, run by the static checks, holds the loader's paths, the kernel's kinds and the nix list to the pins, and fails on a pinned file, an `include_bytes!` of one, or (given the files) any run of their bytes in the tree or in a built capsule or kernel.

## Tests

`userland/mt7921_proofs`: 106 tests, the driver's own source over a modelled chip (register window, ownership, reset, rings, MCU command and event protocol, patch semaphore, download, channel grants) and the shared WPA2 access point simulator. Synthetic firmware images with the real header layouts are built in the tests; no MediaTek file is read. `verification/host_mutants/mt7921.json`: 45 mutants, each removing one rule from the driver's source, all caught.

## Not done

- A boot on a card. Until then nothing here is known to work on hardware.
- A WPA3 join through this driver on the host (no SAE access point in its model).
- The chip's interrupts, power save, hardware scan, key offload, A-MPDU, CLC and SAR tables, 6 GHz, the MT7925.
