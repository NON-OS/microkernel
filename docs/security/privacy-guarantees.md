# Privacy guarantees

What NONOS promises about leaving no trace and leaking nothing. Each promise names its proof and is marked at the level the proof reaches:

- **booted**: shown on a booted image, with the command and its output named;
- **host-tested**: a test runs the real source on a build machine, and a mutant that removes the control is caught;
- **design**: the code is written to hold it, and no test checks it yet.

No claim is rounded up. Where a promise does not hold, this page says so and names the open work.

The network and amnesic rows marked 2026-10-25 refer to the image §7 names for that day, built at a scratch merge of this branch and privacy/power-off. The other booted rows refer to the `standard` profile's development twin at commit 308615832, sealed with throwaway keys (`tools/nonos-dev-image --profile standard`, image sha256 `e1b3cff8…5cd011288`). It carries the shipped feature set, with path-only attestation and the development loader. Like `standard`, it has no capsule serial output (see [the feature inventory](../build/feature-inventory.md)). Section 7 says how it was booted, and what the boots did and did not exercise.

## 1. Nothing persists unless the person chose it

| claim | level | proof |
|---|---|---|
| A boot keeps nothing until first-boot setup records the choice. The policy field `Persistent` starts `false` (`userland/capsule_policy/src/store/defaults/store.rs`), and only setup and settings may write it (`capsule_policy/src/server/handle_set.rs`). Once true it stays true for the boot: a set back to false is refused, as the kernel never turns keeping off (`capsule_policy/src/store/keep_once.rs`). | design; the one-way rule host-tested | `userland/zerostate_proofs` `once_tests`. Mutants: a set to false let through after true, a false set refused while false, a second true refused, only false to true allowed. Each is caught. |
| Until the person chooses to keep things, the kernel refuses every store write that is not an erase, whichever capsule calls it: each byte a write changes must become zero (`EACCES`, `[ZS] store write refused: this boot keeps nothing`, `src/syscall/microkernel/store_write.rs`, `src/security/zerostate/keep.rs`). Keeping is off at every boot and turned on only through the policy push (`KeepAcrossBoots`), accepted only from the pid the kernel spawned the policy capsule as, while it runs, and never turned off within a boot; the policy service pushes it when `Persistent` becomes true, at setup or at the restore (`userland/capsule_policy/src/push/on_bool_set.rs`, `restore/apply.rs`). Not covered: a StoreWrite holder can still reach raw sectors through a disk driver, and every Linux role holds StoreWrite. | host-tested | `userland/zerostate_proofs` (24 tests). Mutants: keeping turned on by another capsule, by an ask to turn it off, by a policy that is not running, by pid 0 or a later pid; a refused ask turning it off; unchanged bytes refused; a one passing; anything passing; the length unchecked; no erase; keeping ignored. Each is caught. |
| vfs asks the kernel whether the boot keeps (`MkKeeping`, `mk_keeping` in `userland/capsule_vfs/src/server/handlers/persist_gate.rs`), never the policy service. Policy's keeper writes the settings record through vfs and waits for the reply; when vfs asked policy back, each waited on the other, the ask failed at its 200 ms deadline, vfs took the boot as keeping nothing and the write was refused, every 5 s (`ipc.call unanswered policy` on serial). The kernel's latch and `Persistent` move together, so the answer is the same one the policy service gives. | host-tested; booted (2026-10-25: before the fix, 59 lines from vfs on an install; after it, 0 on an install, an amnesic boot and a kept boot whose Settings change came back after a reboot, [evidence](privacy-evidence/2026-10-25/keep-354676751/README.md)) | `userland/zerostate_proofs` `cycle_tests` and `once_tests` (random sets leave the two agreeing). Mutants: the gate inverted, the gate always open, the policy client called again, the dependency put back. Each is caught. |
| On a boot that keeps nothing, vfs refuses to keep a file (`EACCES`). A withdrawal there (zeros, an empty file included) touches only a record the disk already holds, at its own length, and erases it where it lies: its payload zeroed, then its descriptor, so the next load reads the slot as empty, neither served nor called damage; a name the disk does not hold is never added (`keep`, `userland/capsule_vfs/src/server/handlers/persist_rule.rs`; `withdraw`, `userland/capsule_vfs/src/blk/store_withdraw.rs`; `erase_slot`, `store_erase.rs`). Every byte it writes is a zero over what was there. On a boot that keeps, a replacement writes the new bytes to a free extent, repoints the entry, then zeroes the extent the record left (`store_replace.rs`); if that last write fails, or the machine stops between the repoint and the zeroing, the old bytes stay in a free extent, and nothing finds and zeroes such an extent later. | host-tested | `userland/fs_proofs`: `vfs_disk::tests_withdraw` (nothing written for an absent name), `tests_withdraw_kept` (erased, every changed byte a zero, gone at the next load with nothing refused; a cut at any sector leaves the record or nothing of it), `tests_withdraw_erase` (a descriptor across two table sectors), `tests_erase`, and `vfs_persist_rule_tests`. Mutants: the descriptor left, the payload left, any length taken, one sector of two, the last byte left, an erased slot called damage, a half-zero slot read as erased; withdraw appending an absent name; the rule passing any byte. Each is caught. |
| On a boot that keeps nothing, removing a store entry is refused and an uninstall drops only the RAM copy (`store_remove.rs`, `store_uninstall.rs` in `userland/capsule_vfs/src/server/handlers/`). | design | none: the boot in §7 removes nothing |
| An idle first boot writes nothing. With the disk driver up for 25 minutes, the data disk is byte for byte as it went in, and every changed EFI variable is one the firmware writes, by GUID and name, the per-NIC record by the NIC's address. Their contents are not judged: `Boot0007`, `MTC` or the per-NIC record would pass with any payload, so a write by NONOS into one of them would not be seen; a diff against a firmware-only boot on the same store would close that. | booted (§7, 2026-10-25: two boots on one machine, each judged) | `scripts/amnesic_boot_check.sh` (§7); `scripts/amnesic_boot_check_selftest.sh` |
| There is no swap or page-out path. | design | no swap, page-out or swapon code exists in `src/` |
| A panic writes no crash record: the handler writes only to serial and the screen (`src/boot/panic/handler.rs`), and nothing calls the kernel's `set_variable` (`src/arch/x86_64/uefi/api.rs`). | design | none |
| The DNS cache lives in RAM only. | design | `capsule_net_dns/src/state.rs`; the image does not ship net.dns, and net.core's resolver keeps no cache on disk |
| Logs live in RAM and on the serial line, and in no file. | design | `src/log/backend/` has a RAM ring, serial and VGA backends, and no file backend |

**Not yet closed:**

- **Persistence after a failed setup restore.** On an installed disk where the setup record fails to restore, `Persistent` is false, but a model import still lands on the disk volume. The kernel picks the volume by whether a data plan exists (`src/fs/blockfs_volume/open_machine.rs`). It should also follow `Persistent`.
- **Removed payloads stay on disk.** Removing a store entry frees its table slot, but the payload bytes stay on disk until they are overwritten (`blk/store_remove.rs`).
- **The payment meter's key.** It keeps its sealed key at `/data/meter.key` on a persistent install (`userland/capsule_payment/README.md`). It is not in the default image.

## 2. RAM is wiped at the end of a boot

| claim | level | proof |
|---|---|---|
| Every power-off and reboot goes through `zerostate::terminate`, which stops the other CPUs, wipes, then powers off. `arch::power::enter` is crate-private, and `terminate` is its only caller. | design, and a model | `verification/lean/Nonos/ZeroState.lean`: `off_was_wiped`, `wipe_covers_every_region` (CI: `lean.yml`). The model covers the region list the code names, and no more. |
| The shutdown wipe covers: device DMA grant frames, each process's code and VMAs, the kernel stacks other than the running one, the file caches, the key vault, the RAM log (if its lock is free) and then the whole heap (`zerostate_shutdown_wipe`, `src/security/hardening/memory_sanitization/api.rs`). | design; parts host-tested | `userland/kernel_proofs`: `dma_wipe`, `ipc_wipe` |
| A process that exits leaves nothing in the frames it held alone: teardown scrubs each user leaf frame, 4 KiB or huge, through the directmap before it frees it; a frame another process still holds, or a device window the broker scrubs, is left (`leaf_release.rs`, `teardown.rs` in `src/memory/paging/manager/address_space/`). The shutdown wipe also zeroes the host and domain names the kernel keeps in statics (`src/sys/policy/hostname/wipe.rs`), under a try-lock said on serial when held. Cost, measured on the build host (a 2.8 GHz Xeon vCPU) with the same `rep stosb; sfence` per 4 KiB frame: 20.6 ms for 64 MiB, 81.9 ms for 256 MiB, 345 ms for 1 GiB, about 3.2 GB/s; before, an exit freed the frames without that cost. | host-tested; booted ([zs-6d87d9aff](privacy-evidence/2026-10-25/zs-6d87d9aff/README.md)) | `userland/zerostate_proofs` `leaf_tests`, `names_tests`. Mutants: the scrub skipped; the free before the scrub; a shared or device frame scrubbed; the names not cleared; only the length's bytes cleared; the length kept. Each is caught. |
| A panic stops the other CPUs and waits, bounded, for each to report itself halted (`smp::others_halted`). It reads the soft-off parameters, zeroes the kernel heap minus its own stack and the kernel image, and powers off. Once the wipe begins it takes no lock, makes no allocation and writes no log (`src/security/zerostate/panic_wipe.rs`). Every kernel-mode CPU exception, an exhausted heap, a shootdown timeout, a stack canary, PQClean's abort, a bad user frame and a failed context restore leave the same way (`boot::panic::fatal`, `src/boot/panic/end.rs`). A fault or second panic on the way out, before the wipe, goes straight to the wipe; the path writes no VGA text, which faulted it from inside a process. | booted (a panic, and a kernel #UD); host-tested (the other fault exits, the stops, `terminate`) | Booted at 58de2bffe, `panicproof-dev` (image `d3a8cd55…`): init's injected panic, then `[ZEROSTATE] panic: cpus halted, wiping, powering off`, and QEMU exited by itself a minute after boot ([`panic-58de2bffe-serial.log`](privacy-evidence/2026-10-25/panic-58de2bffe-serial.log)). The same proof at 3c5695041 faulted on the VGA write and halted unwiped ([`panic-3c5695041-serial.log`](privacy-evidence/2026-10-25/panic-3c5695041-serial.log)). At 08f9fca9f, `faultproof-dev` (image `90c23a9f…`) raised `ud2` in init: `[PANIC UD] … to the panic path`, `[ZEROSTATE] fatal kernel fault`, `[ZEROSTATE] panic: cpus halted, wiping, powering off`, and QEMU exited 59 s after boot ([`fault-08f9fca9f-serial.log`](privacy-evidence/2026-10-25/fault-08f9fca9f-serial.log)). The boots show the order and the power-off, not the zeroes: no dump of RAM was taken. `userland/kernel_proofs` `panic_plan` checks byte for byte that no kept range is wiped and every other heap byte is, the vault's place included, over 400 generated layouts, and that the kept window holds a 16 KiB IST stack wherever it and `sp` stand (mutants: wiping through the kept range; dropping the part above it). `panic_stage`: the claim rule over every order of five entries by three CPUs, and glue over all 17 exception exits and the six mid-session stops (mutants: the owner parks, any CPU wipes, a second wipe, no claim, the word's packing, the wipe mark dropped, the VGA banner back, PF/#DB/OOM/canary/restore halting, a locked serial write). Each is caught. `terminate` parks once the panic path is taken: `tests_terminate` over every order of five terminate and panic entries by two CPUs (mutants: the stage unread, `taken` never, `taken` only once wiping). |
| A capsule cannot reset or power off the machine around the wipe. The PS/2 grant refuses the i8042 reset commands, 0xF0–0xFF and 0xD1, on port 0x64 (`src/hardware/broker/pio/access/reset_rule.rs`). The FADT's reset register is refused to the ACPI capsule's port windows. PM1a and PM1b control are the capsule's (it reads SCI_EN and writes GBL_RLS there), but every port write it asks for is checked first, and one that sets SLP_EN, at any width and offset, in PM1x control or the hardware-reduced sleep control register, is refused (`src/hardware/broker/acpi/rule/sleep_enable.rs`, `port_access.rs`). A driver's PIO grant keeps off all four registers (`src/hardware/broker/pio/power_ports.rs`), and a memory region keeps off any of them the FADT puts in memory. Port 0x92 and 0xCF9 were reserved before this change. | host-tested | `kernel_proofs` `pio_reset` (mutant: the 0xF0 range dropped); `acpi_region` `tests_sleep_enable` (every write of widths 1 to 4 at ten ports, every bit, against a bit-address oracle; both PM1 blocks), `tests_power`, `sleep_enable_glue_tests` and the sweep. Mutants: the width bound, the byte shift, the bit index, any for all, the check dropped from `port_write`. Each is caught. Booted, on a scratch image only (no shipped image carries the ACPI capsule): at ccddcaba8 with the capsule built in, its PM1 event and control ports (0x600, 0x604) were granted, it found the platform `already in ACPI mode`, armed its GPEs and took the power button, and no `event ports refused` line was printed ([`k2b-acpiproof-ccddcaba8-serial.log`](privacy-evidence/2026-10-25/k2b-acpiproof-ccddcaba8-serial.log)). A QMP power-button press 60 s later did not power the machine off: the capsule printed nothing after it, and QEMU was stopped 120 s on. Why the press went unserved is not known yet. On standard-dev (no ACPI capsule, the kernel's own poll) a QMP press brought no confirmation either, likely the same QEMU behaviour: PWRBTN_STS latched only with PWRBTN_EN set ([`walk/README.md`](privacy-evidence/2026-10-25/merge-fd40dd41f/walk/README.md)). |

**Not yet closed:**

- **Closed: the wiped power-off from the desktop.** The shell's Power Off, from the menu or the Power key, asks `power.off`, and nothing served it in a shipped image, so a person's only way off was holding the button, a hardware off that wipes nothing. Now `capsule_power` runs and owns `power.off`, registered by the kernel at spawn, and turns the shell's confirmation into `AdminShutdown`, which is `terminate` (`userland/capsule_power/src/off/mod.rs`). Booted: the menu's Power Off reached `[POWER] leave: …` and QEMU exited 3 s after Enter ([walk](privacy-evidence/2026-10-25/merge-fd40dd41f/walk/README.md)); the ACPI power button, armed once interrupt routing is up, brought the confirmation, a second press stacked nothing, and Power Off ended in QEMU exiting ([P-05](privacy-evidence/2026-10-25/p05-c39b8edd9/README.md)). Holding the button four seconds still forces a hardware off with no wipe.
- **Panic wipe coverage.** A panic does not wipe process memory: finding its frames takes the process table and pager locks, which the panic may hold. Writing allocation-free, try-lock walks of them is the next step.
- **Shutdown wipe gaps.** The wipe does not reach: frames freed through `phys::free` without zeroing (other than a dying process's user frames, now scrubbed at teardown); the kernel's own `.data`/`.bss` beyond the log and the host and domain names; page tables; the framebuffer and any memory on a device (a GPU's VRAM, a NIC's buffers, a disk controller's cache); the CPU's own caches and registers; firmware memory (SMRAM, the UEFI runtime regions, ACPI NVS); the TPM; and the running stack. A power cut or a held power button skips the wipe entirely. The session RAM volume is erased only cryptographically: its key is in the heap, and the heap is wiped.
- **RAM log under contention.** The RAM log is skipped when its lock is held.
- **Booted proof.** `tools/nonos-zero-state-check` at 6d87d9aff: a per-run secret typed into setup was in guest RAM 8 times before Power Off and 0 times after the wipe, with QEMU held at power-off; the boot changed no disk sector and left no copy on the disk; the next boot ran setup from step one ([zs-6d87d9aff](privacy-evidence/2026-10-25/zs-6d87d9aff/README.md)). Two earlier runs found the holes this closed: frames of exited processes, the host name statics, and live memory outside the recorded VMAs. One run, under TCG; real hardware is not covered.

## 3. Network: anonymity networks where the design says so

| claim | level | proof |
|---|---|---|
| The image sends no DNS, NTP, mDNS, LLMNR, SSDP or NetBIOS packet and no IPv6, and talks only to peers it chose: pinned bootstrap hosts, and relays named by a consensus a pinned authority sent. | booted (§7, 2026-10-25) | `scripts/no_telemetry_qemu_capture.sh`, judged by the current `tools/nonos-pcap-egress` on the guest's egress alone (§7): 2284 guest frames, 0 failures, every peer pinned |
| No name is looked up through the resolver unless the chosen network is Direct. Off Direct, net.sockets refuses a connect by name on any socket (`host_target`, `userland/capsule_net_sockets/src/server/handlers/connect/host_target.rs`), and net.core refuses RESOLVE_A itself (`route_gate`, `userland/capsule_net_core/src/server/handlers/dns/route_gate.rs`), so a caller that asks net.core directly, the terminal's `ping` and `nox` among them, is refused too. A store that does not answer is not Direct. Not covered: a capsule holding the Network capability can still send UDP or TCP to port 53 by address, on any route; only that capability gates it, and the egress capture fails any such packet (§7). | host-tested | `userland/capsule_linux_proofs` `mixnet_name_tests`; `userland/net_core_proofs` `dns::route_gate_tests` (every route value, and the gate before any query starts). Mutants: the Direct check dropped in net.sockets; the gate open; the gate dropped from RESOLVE_A. Each is caught. |
| The wallet's RPC never goes Direct (`Route::for_wallet`, `userland/nonos_route_link/src/pick.rs`). Installs go over Anyone by default (`Route::for_installs`). | design | none |
| The image has no time sync, so it sends no NTP. `net.ntp` is not spawned beside `net.core` (`spawn_legacy_stack`). | design | the capture (§7) |
| Telemetry, update checks and captive-portal probes do not exist. | design | grep over `userland/` and `src/` for telemetry, captive, connectivity and update-check endpoints finds none; the capture (§7) |

**Not yet closed:**

- **One Network capability.** A capsule holding it can open a direct socket through net.core or net.sockets whatever route was chosen; the route rule lives in each client (`nonos_route_link`). Splitting it into an anonymous and a direct capability is the fix.
- **Desktop shell's Network grant.** The shell holds Network only to read the DHCP state.
- **Bootstrap before consent.** The Nym and Anyone clients reach their directories and a gateway at boot, before the person has chosen anything, so the local network sees a machine using both (`capsule_net_nym/src/server/runner.rs`, `capsule_net_anon/src/server/idle.rs`).

| claim | level | proof |
|---|---|---|
| Every NIC transmits from a fresh random, locally administered unicast MAC on each bring-up, never the burned-in one (`nonos_mac::apply`, `userland/nonos_mac/src/local.rs`). | host-tested; booted for virtio-net | `userland/nonos_mac/src/tests.rs` and the driver proofs crates; on the boot in §7 the guest sent from `7e:4e:99:54:18:58`, and the NIC's own `52:54:00:12:34:56` only in the firmware's three frames before NONOS ran |
| The image sends no hostname: no DHCP option 12, 60, 77, 81 or 97, and no mDNS. Its DHCP carries no option but 50, 53, 54, 55, 57 and 61 and goes only to broadcast or the server the network named. | booted (§7, 2026-10-25), the firmware's DHCP judged too | the capture's `dhcp-id`, `dhcp-opt`, `dhcp-dst` and `discovery` rules; `--self-test` and `mutants.py` |
| DHCP asks for what Windows 10 and 11 ask for, in their order (`PARAMETER_REQUEST_LIST`, `userland/capsule_net_core/src/iface/dhcp/request_list.rs`), not smoltcp's `[1, 3, 6]`, which marked a NONOS machine on any LAN. | host-tested; booted | `userland/net_core_proofs` `dhcp::tests` takes net.core's first DHCPDISCOVER off a smoltcp link (mutant: the list not set, caught); the capture in §7 shows the list on the wire |
| Scripts in the browser see UTC: `localtime_r` is stubbed to zero (`userland/nonos_qjs/vendor/stubs.c`), and no client sends a `Date` header. | design | none |
| Scripts in the browser get no font list, screen size or `hardwareConcurrency`. | design | the DOM prelude (`userland/nonos_qjs/vendor/dom_prelude_1.inc`) exposes none of them |

**Not yet closed:**

- **TLS fingerprint.** The TLS ClientHello is NONOS's own: two cipher suites, five extensions in a fixed order and no ALPN (`userland/nonos_tls/src/client_hello.rs`). Its JA3/JA4 marks every NONOS client to an exit or a server.
- **Browser headers.** The browser claims Firefox 128 (`capsule_browser/src/browser/http/request.rs`), while its Accept header, HTTP/1.1 and TLS do not match Firefox.
- **Self-naming User-Agents.** The Linux installer, model fetch, `nox` and Nym's directory fetch name themselves `nonos…`.
- **DHCP residue.** The DISCOVER matches Windows 10 and 11 on option 55, byte for byte, but not on everything. Its options go out in smoltcp's order, 53, 61, 57, 55, where Windows sends 53, 61, (50), 12, 60, 55. NONOS sends no hostname (12) or vendor class (60): `MSFT 5.0` would copy Windows a step further, but option 12 names the machine and option 60 the software, and the egress judge fails both (`dhcp-id`). Option 57, which Windows does not send, is smoltcp's and stays. What a real Windows 11 capture on the same network would settle, and none was taken: the broadcast flag, the `secs` field, the client identifier's type, and whether option 116 is sent.
- **The Nym validator's name is sent in the clear.** The Nym client's directory fetch sends `validator.nymtech.net` as its TLS server name, in the clear, to 92.39.63.14:443 (52 times in the §7 capture). The host is pinned by address and never resolved, but the name shows anyone on the path that this machine uses Nym. Encrypted Client Hello would hide it, and `nonos_tls` has none (`client_hello.rs`).

## 5. Keys

| claim | level | proof |
|---|---|---|
| A capsule's keys are generated, kept and used in the keyring capsule. The keyring answers each caller only for keys it owns, by the pid the kernel stamps; it never trusts a pid from the payload (`resolve_caller`, `userland/capsule_keyring/src/server/caller.rs`). | design | none |
| Reaching the keyring takes the Keyring capability: the kernel admits a sender to the `keyring` endpoint only with it (`KEY_SERVICES`, `src/services/registry/policy.rs`). | host-tested | `kernel_proofs` `service_policy_tests` (mutant: the keyring branch dropped, caught) |
| Keys outside the keyring are wiped when done. A TLS connection's secrets and record keys live in one heap block a `TrafficKeys` points to, written there in place by the key schedule, so moving the keys copies a pointer, never a secret; the block is zeroed on drop (`userland/nonos_tls/src/traffic_keys.rs`). The flight's two private keys are boxed the same way, wiped on drop and at every connection's settle (browser, wallet, terminal), and the ECDHE secret, every HKDF block, the MAC's output and the Finished key are wiped once used. What is not wiped: the internal state of the `hmac` 0.12, `sha2` 0.10 and `blake3` crates (net.nym's hashing, in the proofs and the capsule), which these versions cannot zero; and the `NonZeroScalar` that P-256's `diffie_hellman` takes, a `Copy` value of the private scalar that can stay in a stack slot (`p256_share.rs`). The ECDHE secret itself is written into the caller's buffer and never returned by value (`server_keys.rs`). net.nym's identity seed is wiped on each copy's drop, in the request that installs it, and with every request's bytes once the request is served (`server/serve_one.rs`). The identity itself is fresh each boot and held for the whole boot by design: net.nym does not clear it, and only the shutdown wipe does. The gateway key lives in one slot and is never copied out: each frame borrows it under the lock (`with_gateway_key`), and the Gateway record copied into the table and every session no longer carries it. It is wiped where it lies when its link is lost (`gateway_lost`), or when a gateway is set on any other connection. The handshake's Diffie-Hellman result and extracted key are wiped, as are every HMAC and HKDF buffer and the ephemeral on drop, whatever the outcome. net.anon's client key has a wiping Drop. | host-tested: the TLS keys' block and move, the flight's keys, the identity's drop, the key slot through `Table::set_gateway` and the clear `gateway_lost` makes, and the HKDF against a reference. Source-checked: where the handshake, establish, set_identity and serve_one wipe. | `tls_proofs` `key_wipe` and `wipe_glue`, and the RFC 8448 schedule vectors through the reworked schedule; `nym_reply_proofs` `secret_wipe_tests`, `key_slot_tests`, `hkdf_tests`, `wipe_glue_tests`. Mutants: an empty Drop, each wipe removed, the key kept across links, a lost link keeping its key, a borrow with no key held. Each is caught. |
| A locked keyring entry is marked locked and stays in RAM until the process ends; the shutdown wipe takes it. | design | `userland/capsule_keyring/src/store/lock.rs` |

**Not yet closed:**

- **capsule_crypto.** `x25519_public` leaves its local copy of the private key unwiped.
- **The payment meter's MAC key.** It is held for the whole boot and never wiped.

## 7. Booted evidence

### 2026-10-25, with the current tools

Every run boots one image: the `standard` profile's development twin (`tools/nonos-dev-image --profile standard`, throwaway keys, sha256 `b1a79ab1…0e3cd4e`) built at a **scratch merge**, fd40dd41f, of privacy/k-series 6c1848052 and privacy/power-off 1b9afc7ea, never pushed (`merge-fd40dd41f/heads.txt`). QEMU 11.1.1 with OVMF, q35 with an Intel IOMMU (`--lane iommu=intel`): a release image refuses device DMA no IOMMU confines. No KVM, so the CPU was emulated (TCG). Each run lasted 25 minutes and nobody answered first-boot setup.
