# NONOS 0.9.3 release notes: Security limits

Part of [NONOS 0.9.3 release notes](0.9.3.md).

### Security limits

[Protections and
limits](../security/protections-and-limits-what-nonos-does.md#what-nonos-does-not-address)
states each of these with the code behind it.

- On a machine whose firmware left VT-d or AMD-Vi off, so no remapping unit is
  in service, a Standard boot goes on with device DMA unconfined: a claimed
  device may reach all of memory. The boot says so on its `[IOMMU]
  posture=dma-unconfined` line, in the attestation, on the splash and in
  About (`nonos-dma-unconfined-posture` in `Cargo.toml`;
  that line under QEMU
  ([kvm-guest-gate](../release-evidence/0.9.3/kvm-guest-gate/README.md),
  instead (3d5569670). See
  [IOMMU](../kernel/iommu-per-capsule-domains.md#when-remapping-is-not-in-service).
- On a Standard boot, two vendor drivers may share an isolation group when
  only a port without ACS joins their devices. Each device keeps its own IOMMU
  domain, but traffic between the two devices is not stopped by the hardware.
  The serial line is `[VT-D] shared: ...`; Hardened and Air-Gapped refuse the
  claim (3b5bb25c8f, `src/hardware/broker/confine/group_share.rs`).
- A device firmware reserved memory for keeps those ranges while no driver
  has claimed it, and a device found through ACPI gets no domain.
- The orderly power-off and restart run the wipe, but it misses kernel
  statics: the data volume key, the token MAC key and the kernel's in-memory
  copy of its console lines. It also misses a live stick's in-memory volume
  ([Device secrets and
  keys](../security/device-secrets-and-keys.md#wiped-at-shutdown-and-reboot)).
  A kernel panic wipes the kernel heap and powers off, but not process memory
  (`src/security/zerostate/panic_wipe.rs`). A forced power-off or a power cut
  wipes nothing.
- The TPM exchange that derives machine keys is unbound and unsalted, so a key
  crosses a discrete TPM's bus in the clear. Any program holding Crypto can
  derive any machine key label except the kernel's own.
- From the moment the installed system prepares an update until the next
  boot, a kernel the release approved opens the data volume on this
  machine's firmware and Secure Boot state, whatever bootloader measured it.
  With Secure Boot off, a bootloader that measures an approved kernel and
  then starts another would open it, and a copy of the disk taken in that
  window keeps the handover record. Prepare right before the update. See
  [The handover](../security/device-secrets-and-keys.md#the-handover).
- Without a TPM, every boot entry but Hardened and Air-Gapped boots with
  rollback protection off, and the kernel's check of the loader rests on the
  loader's own word. With Secure Boot off, an image sealed whole with other
  keys passes the loader's and the kernel's checks. See [Boot chain and
  signatures](../security/boot-chain-and-signatures.md#secure-boot).
- The package store is written to the disk unencrypted. Only the data volume,
  and records a program seals itself, are protected there.
- The kernel image sits at a fixed address, the kernel has no stack canaries,
  and the kernel stack a process makes its system calls on has no guard page.
  KPTI is not implemented and the L1D flush is never issued, so
  Meltdown-affected parts are not mitigated.
- Authority follows the process, not the code: an attacker who takes over a
  capsule gets every capability it holds.
- `net.nym` and `net.anon` start on every boot that starts the network,
  whatever the default, so the local network can see that this machine runs
  Nym and Anyone ([Mission](../overview/mission.md#what-nonos-is-not)).
- A Linux app's home is its own and lasts until power off. Nothing an app
  keeps survives a reboot, so the only lasting copy of a wallet seed is the
  one written down.
